# Resigning a forced mate — 2026-09-12

Owner's brief: "if there is forced checkmate (against us) in less than 3 moves, we should wait
for a random amount of seconds (1–8) like evaluating the forced mate — then click the resign
button and then click confirm — instead of waiting it out."

This note records the rule as built, its knobs, the click sequence, the selector ladders the
content adapter tries, and the one thing only a real chess.com board can answer.

## The rule

The trigger lives in `GameSession.shouldResign` (`src/service/game-session/session.ts`) and
fires on the recommendation path, at the point where an armed hand would otherwise be handed
the move (`actOnRecommendation`). All of the following must hold:

1. The recommendation's **best line** (`multipv 1`) has a mate score against the side to move:
   `score.mate < 0` and `-score.mate <= RESIGN.maxMateIn` (3). `mate -3` resigns; `mate -4`
   plays on.
2. That line's search `depth >= RESIGN.minDepth` (8), so a shallow blip from a search that was
   cut short never resigns a game.
3. **Every** scored line is mated (`score.mate < 0` on all of them) — nothing escapes.
4. Auto-move is armed, the live profile allows automatic moves, the master switch is on and
   the colour is known (`mayActOn`), and it is our turn.
5. No resignation has been attempted yet in this game (`resignAttempted`, reset by
   `startGame`). Once per game, whatever the outcome of the attempt.

A clock race is deliberately not considered: the mate is forced, so the position is resigned
regardless of the clocks. A recommendation from the opening book (no lines) never triggers.

## The knobs (`src/core/constants/resign.ts`, C1)

| Knob | Value | Meaning |
|---|---|---|
| `RESIGN.maxMateIn` | 3 | Resign when mated in at most this many moves (UCI `mate -N`). |
| `RESIGN.minDepth` | 8 | The best line must come from a search at least this deep. |
| `RESIGN.delayMs` | 1000–8000 | The "evaluating the forced mate" pause before the resign click. |
| `RESIGN.confirmDelayMs` | 350–1100 | Between the resign click and the confirm click. |
| `RESIGN.targetTimeoutMs` | 2000 | Port budget for one `resign` target read / revalidation. |
| `RESIGN.confirmWaitMs` | 4000 | How long the confirmation is polled for after the resign click (the popup animates in). |
| `RESIGN.confirmPollMs` | 150 | Interval between those polls. |

The delay is drawn with `sampleRange(RESIGN.delayMs, rng)` from the session's per-game stream,
so two games never wait the same time.

## The sequence

```
recommendation (mate -N ≤ 3, depth ≥ 8, all lines mated, hand armed)
  → session logs "forced mate against us — resigning instead of playing it out"
  → session timer: sampleRange(RESIGN.delayMs)          (cancelled like any session timer)
  → ResignInput.attempt(tabId, signal)                  (src/service/resign-input.ts)
      1. port `resign { step: "resign" }`                → content: SiteAdapter.resignTarget("resign")
         (re-read after ensureAttached: the infobar can shift the layout)
      2. hand walks to the control (generatePath, per-move motor profile) and clicks it through
         CdpInputBackend — revalidated by targetId + point before the press and during the hold
      3. sleep sampleRange(RESIGN.confirmDelayMs)
      4. port `resign { step: "confirm" }`, polled up to RESIGN.confirmWaitMs
      5. same walk + held click on the confirmation
      → { status: "resigned" }
  → the site ends the game; `gameEnded` reaches the session as usual
```

Outcomes other than `resigned`:

- `not-ready` (no control found at either step, or a control that moved under the hand): the
  session logs "resign control not found — playing the move instead" and schedules the
  recommended move with its plan re-planned for the wait (`repaced`, `withheld-then-released`),
  so the game never stalls. The attempt is not repeated in that game.
- `aborted`: the session withdrew — a new position arrived, the hand was disarmed, the game
  ended, the assistant was switched off or the session was disposed. Nothing more happens.

Guards are the ones `NewGameInput` uses: the game port connected, the debugger attached, page
focus held (the armed hand's own reservation is borrowed; otherwise a reservation of the
action's own is taken and released afterwards), `FocusGate.canExecute`, one attempt per tab.
A press admitted by Chrome always gets a release — off-page (`NEW_GAME_INPUT.cancelPoint`) on
abort, so a moved control is never clicked. The content script only ever reports a rect; it
never clicks anything (§13.3).

## The selector ladders (`src/content/adapters/selectors.ts`)

Discovery is `resignControl(doc, win, step)` in `src/content/adapters/resign.ts`: walk the
ladder in order, take the first element that is rendered, enabled (`actionDisabled`,
`:disabled`, `pointer-events: none` all reject) and **positively labelled** for the step. A
generic container entry can therefore never resolve to "Draw" or "Abort".

`resign` (positive label: text `/^resign$/i`, or `aria-label` / `title` matching `/\bresign\b/i`):

```
[data-cy="resign-button"]
[data-cy="game-controls-resign-button"]
button[aria-label="Resign"]
[aria-label="Resign"]
.resign-button-component
.game-controls-component button
.game-controls-container button
.board-layout-controls button
```

**The confirmation is a popup that appears after the resign click** (the owner, 2026-09-12), and its
markup is unknown — so it is found first by *what appeared*: when the resign control is read the
adapter snapshots every visible, usable clickable control (`resignAnyControl`:
`button, [role="button"], a[href]`); at the confirm step any control **not in that snapshot**,
positively labelled (`resignConfirmTextRe`: "Yes", "Yes, resign", "Resign", "Resign game",
"Confirm", "OK"), and not the resign control itself is the confirmation, one inside a dialog-like
container (`resignPopup`) ranking first. "Cancel" / "No" never match. Only if nothing new matches
does the ladder below run.

`resignConfirm` (positive label: `resignConfirmTextRe`):

```
[data-cy="resign-confirm-button"]
[data-cy="confirm-resign-button"]
button[aria-label="Yes"]
.board-modal-container button
.confirm-button
.game-controls-component button
.game-controls-container button
```

Only a page whose kind is `live-game` or `vs-computer` answers; everything else is `not-ready`.
The confirmation step **excludes the element discovered as the resign control**: its label may
legitimately read "Resign" (which the confirm regex accepts), and without the exclusion the
resign control would be rediscovered as its own confirmation and clicked twice.

## Open QA item: the real chess.com markup

chess.com's live-game markup for the resign control and its "Resign?" confirmation is **not**
captured in `test/fixtures/` (the fixtures were taken with no game controls rendered), so the
ladders above are plausible candidates, not verified selectors. The simulator and the unit tests
exercise the mechanism against the labels the ladder accepts, not against the site.

**How to check on a real board** (one live game against a bot is enough, `/play/computer`
renders the DOM board):

1. Load the dev build, arm auto-move in the waiting view, and get into a lost position (or
   temporarily lower `RESIGN.minDepth` / raise `RESIGN.maxMateIn` in a scratch build).
2. When the engine reports the mate, the Engine view's log shows
   `game-session: forced mate against us — resigning instead of playing it out` with the
   sampled `delayMs`.
3. If the content script cannot find a control it writes
   `content: no resign control found for this step { step: "resign" | "confirm" }` to the same
   log (the content logger is bridged to the Engine view), and the session then logs
   `resign control not found — playing the move instead`. That log line names the step whose
   ladder missed.
4. In that case inspect the page: the control's `data-cy`, `aria-label`, class and text, and
   the confirmation's container and button. Add the real selector at the **top** of the
   matching ladder in `selectors.ts`, and extend the positive-label regex only if the real
   label is not "Resign" / "Yes". Capture the markup into a fixture so
   `test/content/adapters/resign.test.ts` can pin it.
5. Also verify the click order on the real page: the resign control on chess.com may open an
   inline "Resign?" row rather than a modal; the `confirm` ladder's
   `.game-controls-component button` entry with the `Yes` / `Resign` / `Confirm` label is
   there for that shape. If the site resigns on the *first* click with no confirmation, the
   attempt currently reports `not-ready` at the `confirm` step after `RESIGN.confirmWaitMs`
   and falls back to playing the move — which by then will not exist. Record what the page does
   and adjust: a `resigned` answer on a first click that ended the game is the likely change.

## Tests

- `test/behavioral/game/resign.test.ts` — the whole stack on the simulator: mate in 2 → delay
  within `RESIGN.delayMs` → resign click inside the control → confirm click inside its control
  → game over, no move played; mate in 4 → the move is played; shallow search → played; a line
  that escapes → played; unarmed → nothing; a position arriving during the delay → cancelled;
  no control → the move is played and the attempt is not repeated.
