# Playing sessions and queue input

Auto-queue now plays consecutive games in sessions. The default session duration is sampled once between 20 and 60 minutes. Games inside that period retain the short 0.9–2.6 second queue pause. At the end of the first game that crosses the session deadline, a break is sampled once between 5 and 20 minutes. The active game is never interrupted to meet the deadline. The next observed game after a break starts a new session.

All four duration endpoints are configurable in Settings → Execution. Imported ranges are finite, bounded and ordered; editing one endpoint across the other moves its companion endpoint too. Old per-game delay settings are dropped. Changing settings affects future samples, without restarting a pending break. The waiting view distinguishes a session break from ordinary queueing and matchmaking. Existing statistics remain intact across playing sessions.

Playing-session progress and absolute break deadlines persist in session storage. Active games have no queue alarm; pending breaks and retries share the earliest persisted wake alarm. Reconnects and duplicate game-end events do not resample a deadline or double-count a game. New games clear only the old queue request, preserving the playing session. Disabling auto-queue, stopping the assistant, closing the tab or navigating away clears the session and its queue intent.

Restart controls are discovered and revalidated by the content adapter. The service worker activates them using the existing generated mouse paths, virtual cursor admission and CDP press/release. Control identity, bounds and hit target are checked before pressing and releasing. Each lobby step uses fresh discovery. Queue-only input does not arm automatic moves, and cleanup preserves a newer game's cursor and focus reservation.

Regression coverage includes consecutive games followed by a break; no interruption at the deadline; worker/session recovery; duplicate completion events; cancellation; settings normalization and endpoint controls; and the break countdown. The settings and waiting views were visually inspected at 420 × 900 in the browser fixture, with no console errors.

Native input was also checked in an isolated headless Chrome localhost fixture using the production mouse helper, path generator, adapter, virtual cursor shield and input tracker. “New Game” followed by “Play” produced two trusted native clicks with 196 dispatched mouse points and 198 cursor updates. The approaches lasted 1,728 ms and 1,602 ms; button holds were 79 ms and 137 ms. The third request observed matchmaking and sent no click. Automatic moves stayed unarmed, temporary focus was restored, and no cursor elements remained. Evidence is in `build-logs/playing-sessions/native-results.json`; the local runner is `/tmp/sliced-newgame-qc/check.ts` (`bun --define __SL_LICENSE_ENFORCE__=false /tmp/sliced-newgame-qc/check.ts`, with its isolated Chrome profile running). This verifies the browser input path on a fixture; it does not claim a live matchmaking run.

The input tests cover moved, replaced and covered targets; movement during a held press; cancellation and disconnects; rejected page receipts; multi-step lobby controls; hidden-cursor preference; borrowed focus; and a new game taking cursor/focus ownership during release. A content regression verifies that restart hit testing opens the virtual shield's small aperture without admitting a native event. The registry regression runs with auto-queue enabled and auto-move disabled, verifies the complete cursor and click sequence, observes the next game, and confirms auto-move remains unarmed.
