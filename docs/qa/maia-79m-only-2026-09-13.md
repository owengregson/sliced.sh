# Maia-3: one size, 79M, for every rating — 2026-09-13

The owner's instruction, verbatim: "remove all the maia models except the largest one (and use
that for all elos — but of course still request moves at the elo we choose etc.)". This records
what was removed, what the single size costs per move against the pipeline's windows, and what
only a browser can answer. The design it amends is
[`maia-selection-2026-09-11.md`](maia-selection-2026-09-11.md); the measurements it leans on are
[`../research/maia3-feasibility-2026-09-11.md`](../research/maia3-feasibility-2026-09-11.md)
§3.5–§3.7 and `docs/models.md` §8.4.

## What did not change — the rating

The query is what it was apart from the `size` field. `recommendation.ts` `queryPolicy` still
issues `{ size, fen, historyFens, selfElo, oppoElo }` with `selfElo = maiaSelfElo(...)` (the
target, form, the H2 slider offset, the pressure reduction, H5's context penalty) and
`oppoElo = opponentElo ?? selfElo`; `maia-session.ts` `predictedPolicyInputs` builds the same
query for the predicted position (`ownMoveMaiaElo`), and the H15 prior above `MAIA.eloMax` still
clamps to `topCalibratedElo` (2700). Both were re-read for this change and not edited. The model
divides the ratings by 5000 and clamps to `[0, 1]` inside the graph (`MAIA_INPUT.eloScale`), so
the Elo slider acts on the model through exactly these two floats — the 79M model at 800 is the
paper's 800, not a 2600 player told to blunder.

## Per-move cost: 79M against the pipeline's windows

Single-threaded wasm under Bun (feasibility §3.5, fp16w; the offscreen document runs the same
wasm with up to `LIMITS.policyInferenceThreadsMax` = 4 threads, which is **not** measured):

| | 79M |
| --- | ---: |
| query p50 / p95 / max | 184 / 214 / 282 ms |
| session create | 716 ms |
| warm-up query (first `run`) | 300 ms |
| RSS after create (Bun process, upper bound on the wasm heap) | +895 MB |

Against the search windows (`SEARCH_BUDGET.moveMs`: bullet 400, blitz 600, rapid 1,000 ms; floor
`minMovetimeMs` 150 ms) and the shaped-search bounds (`MAIA_SEARCH.shaped`):

1. **The query runs in parallel with the search** and the selector uses the answer when it lands
   within `MAIA.inferenceBudgetMs` (1,500 ms) of being issued. At bullet a 184–282 ms query is
   inside the 400 ms window; at the 150 ms floor (a clock race) the engine selects anyway
   (`clockRacePolicy`). **No test shows a bullet move losing Maia** —
   `recommendation.test.ts` "a fresh answer inside policyFirstMs shapes the search over Maia's
   roots alone; a slow one falls back to the broad search" is about the search's *shape*, and its
   slow branch still selects from Maia's answer once it lands. `inferenceBudgetMs` therefore stays
   at 1,500 ms; it was sized for the 79M query plus a cold load in the first place.
2. **`policyFirstMs` (120 ms) is below the 79M p50.** On our own turn a *fresh* query will not
   normally shape the search; the pipeline falls back to the broad search plus the extra
   `searchmoves` pass, as the 2000–2600 band already did. What carries the shaped search for every
   rating now is the H7.3 pre-inference on the opponent's clock: `preInferWaitMs` (300 ms) is
   above the single-threaded p95 (214 ms), so a correct reply prediction still arrives as a cache
   hit. Whether 120 ms should move is a browser question (item 2 below), not a Bun one — the
   4-thread wasm figure is unknown.
3. **Cold load is paid once, before any game.** `game-stack.ts` sends
   `configure.warmPolicy = MAIA.defaultSize` (79M) on the engine's first connect, so the ≈ 1 s
   (create + warm-up) plus the 156 MB package read happen on the offscreen document's main thread
   at connect time — earlier than the waiting view, never inside a move window. The game-start
   warm (`startGame` → `warmPolicyFor(target, true)` → `policy-warm`) then answers `loadMs: 0`.
   The one remaining cold path is an offscreen document recreated mid-game (its reconnect
   `configure` re-warms 79M); the budget covers one such move.
4. **CPU contention** (feasibility §3.5 "Interpretation"): a 200 ms single-threaded run on the
   offscreen main thread delays UCI line routing while Stockfish searches on
   `clamp(cores − 2, 1, 4)` threads. With 5M this was ≈ 20 ms; it is now the 79M figure for every
   rating. Threads should cut the wall clock, not the CPU-seconds.

## Open browser items (cannot be measured under Bun)

1. **Resident memory with the 79M session next to Stockfish.** The feasibility study's +895 MB is
   the Bun process RSS after `InferenceSession.create` (fp16 weights unfold to fp32; the
   4 GiB wasm maximum is not the concern). The offscreen document also holds Stockfish's shared
   memory (`LIMITS.engineMemoryInitialPages` = 160 MiB initial, 512 MiB max) and up to two
   ChessMimic sessions. Measure the document's memory (`chrome://memory-internals`, or the task
   manager's per-process figure) with the session warm and a search running; the number to
   record is the peak during a blitz game. This was the "could not fit next to a large hash" item
   of the 2026-09-11 open list and is now unconditional.
2. **Warm query latency in the offscreen document with 4 threads, under engine load**, p50/p95
   over a game — the number `policyFirstMs` and `preInferWaitMs` should be judged against.
3. **Cold-load time at the first game**: from the engine's first `configure` to the
   `policy-status` reply (`loadMs`), including the 156 MB `fetch(chrome.runtime.getURL(...))`
   the study did not time, and whether the first move's `timing.prepare` ever waits on it.
4. **`docs/third-party.md` regeneration.** The notice is generated by `bun run vendor:engine`
   (never hand-edited) and still lists the 5M / 23M rows; it needs one regeneration run after the
   files are deleted. `test/scripts/vendor-engine.test.ts` only checks the 79M rows are present,
   so nothing fails until then.
